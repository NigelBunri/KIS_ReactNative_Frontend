# UX/UI Audit — Phase 1 Inventory: Partners Components

**Scope assigned:** `src/components/partners/**` — **87 files.**
**Files inventoried: 87 / 87.** Nothing outstanding.
**Pass type:** Read-only inventory. No source files were edited. No builds/tests were run.

## Summary

This is the largest single component domain in the app and backs the entire "Partners" tab — both the per-organization admin/management surface (dozens of slide-over panels reached from Settings) and the platform-wide KCAN super-admin console. The directory has a clear hub-and-spoke shape, confirmed by import tracing (not just naming convention):

- **`src/screens/tabs/partners/PartnerPanels.tsx`** (784 lines) is the real mounting hub for the per-partner management panels — it imports and conditionally renders ~41 of the `Partner*Panel.tsx` components in this directory (PartnerAuditPanel, PartnerAutomationPanel, PartnerMembersPanel, PartnerTasksPanel, PartnerRolesPanel, PartnerChannelsPanel, PartnerVerificationPanel, etc.) based on which settings section/feature was tapped in `PartnerSheet.tsx`.
- **`src/screens/tabs/PartnersScreen.tsx`** is the hub for the KCAN **super-admin** console — it imports all 9 `Admin*Panel.tsx` components plus `AppBuilderPanel`, `GeolocationPanel`, `CreatePartnerScreen`, and the settings-catalog files. These are gated server-side on `is_superuser`/`is_staff` viewing the KCAN partner.
- **`src/screens/tabs/partners/PartnerLayout.tsx`** mounts the three structural panes: `PartnersLeftRail`, `PartnersCenterPane`, `PartnerAppLaunchBar`.
- **`PartnersCenterPane.tsx`** mounts the `center/*` section components (admins strip, channels/communities/courses/groups sections, header section).
- **`PartnerDiscoveryPanel.tsx`** mounts `discovery/*`; **`PartnerAutomationPanel.tsx`** mounts `forms/*`; **`PartnerRecruitmentPanel.tsx`** mounts `recruitment/*`; **`PartnerReportsPanel.tsx`** mounts `reports/*`; **`AppBuilderPanel.tsx`** mounts `TabTemplateManager.tsx`.
- **`App.tsx` / `src/contexts/DetachedPartnersOverlayContext.tsx`** mount `PartnerSheet.tsx` and `PartnersMessagesPane.tsx` directly (these are the only two components in this scope reachable from the true root, matching the pattern seen in prior batches — most partner UI is reached by in-app state, not route registration).
- A separate, less obvious consumer: **`src/screens/partners/OrganizationAppScreen.tsx`** (outside this scope) mounts `DashboardTab.tsx`, `LocationAttendanceTemplate.tsx`, `PartnerBibleScreen.tsx`, `PartnerMessagingView.tsx`, and `PartnerFeedPage.tsx` — these five are rendered **inside a partner's own branded mini-app** (per-tab templates configured via `AppBuilderPanel`/`TabTemplateManager`), not inside the admin management UI at all. They are a distinct "public-facing partner app" rendering path.

**Dead code found:** `src/components/partners/partnersMockData.ts` has **zero references anywhere in `src/` or `App.tsx`** — not imported by any screen, panel, or test. It exports `MOCK_PARTNERS` seed data (`Kingdom Builders Intl`, `Youth Impact Network`, `Hope Health Foundation`, ...) that appears to predate the real `/partners/` API integration (`usePartnersData.ts` now fetches live data) and was never deleted. This is a genuine unused-file finding, not a "mounted imperatively" false negative — confirmed by reading the file and grepping for `partnersMockData` and `MOCK_PARTNERS` repo-wide.

A few other things stood out:
- **Honest-empty-state pattern used deliberately in two places**: `PartnerFeaturePanel.tsx` is a documented fallback for settings-catalog features with no backend behind them yet — its own header comment explains it replaced a fake "editable" config form that silently did nothing. `PartnerLeadershipPanel.tsx` and `PartnerAnalyticsPanel.tsx` both compute real metrics server-side but return an `unavailable_metrics` list for catalog entries that have no real data source, and the UI shows that honestly rather than fabricating numbers. This is a recurring, intentional product decision across the codebase worth preserving in any redesign.
- **Two same-named-sounding panels are intentionally distinct**: `AdminAnalyticsPanel.tsx` (KCAN-staff platform-wide) vs. `PartnerAnalyticsPanel.tsx` (one partner's own data) — explicitly called out in both files' header comments to prevent confusion. Same split pattern exists for `PartnerTasksPanel.tsx` (single-channel board, opened from chat header) vs. `PartnerTaskBoardsPanel.tsx` (cross-channel admin overview, opened from Settings) — they share a backend model and the task-detail view behaves identically in both.
- **Near-universal CRUD-panel template**: the majority of `Partner*Panel.tsx` files (roughly 30+) follow one shape almost exactly: `isOpen`/`panelWidth`/`panelTranslateX`/`partnerId`/`onClose` props, a slide-over `Animated.View`, `getRequest`/`postRequest`/`patchRequest`/`deleteRequest` from `@/network`, local `loading`/`error` state, `ActivityIndicator` + `Alert.alert` for feedback, and `partnersStyles.ts` for shared styling. This uniformity is good for a redesign — a single pattern change (e.g. swapping the loading/error treatment) would propagate to most of the domain at once. The outliers worth noting during the real audit pass: `PartnerSheet.tsx`, `PartnerSpacesDirectoryPanel.tsx`, `PartnersLeftRail.tsx`, and `PartnersMessagesPane.tsx` show **no loading/error/empty-state handling at all** (grep found zero matches for `ActivityIndicator`, `loading`, `error`, `catch`, `Alert.alert`) — they are pure prop-driven presentational components, so that may be fine, but it's worth a second look given how central `PartnerSheet` and `PartnersMessagesPane` are (both root-mounted).
- `partnersStyles.ts` and `partnersTypes.ts` are the true shared backbone — `partnersStyles` is imported by 50+ files, `partnersTypes` by 23+.
