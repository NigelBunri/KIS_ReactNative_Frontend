# Screens Inventory: `src/screens/tabs/**` + root-level `src/screens/*.tsx`

**Scope.** This domain covers the core navigation/tab surface of the KIS app: the 5 bottom-tab
screens (Messages, Bible, Broadcast, Partners, Profile) and everything nested under them
(`src/screens/tabs/**`, 134 files — sub-tabs, panel-state hooks, profile editor modals, Bible
Games engine, partner admin panels), plus the 29 screens that sit directly under `src/screens/`
as root-level stack routes (auth/onboarding, settings, device/account management, search). Route
names were cross-checked against `App.tsx` (`RootStack.Screen` registrations) and
`src/navigation/AppNavigator.tsx` (the `Tabs.Navigator` that actually mounts `MainTabs`, and the
nested `Tab.Navigator` inside `MessagesScreen.tsx` for its Chats/Updates/Calls/Communities
sub-tabs) rather than assumed from file names.

**Coverage.** All 163 assigned files were inventoried (134 under `src/screens/tabs/**` + 29
root-level `src/screens/*.tsx`). Nothing is marked NOT YET INVENTORIED. Depth varies
intentionally: screens and substantive hooks got full header+signal review; the ~34
byte-for-byte-identical partner slide-panel hooks (see finding #3 below) got one full read of
the canonical copy plus a diff-verification pass across the rest, since reading each one in the
same depth would have added no new information.

**Notable findings from this pass (full detail in the table and inline notes below):**

1. **`src/screens/tabs/HealthcareScreen.tsx` (4,228 lines) appears to be dead code.** Grepped the
   whole repo (excluding other worktrees) for any import of `tabs/HealthcareScreen` — zero hits.
   `BroadcastScreen.tsx`'s "healthcare" tab renders `BroadcastHealthcarePage` from
   `../broadcast/pages/BroadcastHealthcarePage` instead, a completely different component. This
   is the single largest file in the whole assigned scope and it is not reachable from any route,
   any nested tab, or any conditional mount found.
2. **`src/screens/CommentThreadScreen.tsx` is also dead code.** Not imported in `App.tsx`, not in
   `RootStackParamList`, and `grep` for `CommentThreadScreen` across the repo (outside worktrees)
   only matches the file's own internal declarations. It defines its own local
   `CommentThreadRouteParams` type rather than extending the shared navigator types, which is a
   symptom of a screen that was built but never wired in.
3. **`src/screens/tabs/MesssagingSubTabs/HubTab.tsx` (439 lines, a full "Channels & Broadcasts
   hub" screen with its own data fetching, search, and modal) is also unreferenced anywhere** —
   not in `MessagesScreen.tsx`'s `Tab.Navigator` (which only wires Chats/Updates/Calls/
   Communities), not lazily required. Three confirmed-orphaned screens in one domain is a pattern
   worth flagging for Phase 2: route-registration audits should not assume "file exists in
   `screens/`" implies "reachable."
4. **Massive duplication in `src/screens/tabs/partners/`:** 34 of the 46 `usePartnerXXXPanel.ts` /
   `useAdmin*Panel` hook files (e.g. `usePartnerChannelsPanel.ts`, `usePartnerActivityPanel.ts`,
   `usePartnerAuditPanel.ts`, `usePartnerGovernancePanel.ts`, …) are byte-for-byte identical
   slide-in-panel open/close/animate boilerplate (confirmed via `diff` after normalizing the hook
   name) — the exact same `isOpen`/`panelWidth`/`panelTranslateX`/`open()`/`close()` shape copy-
   pasted 34 times, plus ~5 more near-identical variants with a parameter added
   (`usePartnerCreatePanel`, `usePartnerFeaturePanel`, `useAppBuilderPanel`,
   `useGeolocationPanel`, `usePartnerOrganizationAppsPanel`). This is ~1,600 lines that could
   collapse to one generic `usePartnerSlidePanel(width, options?)` hook. Not a UX bug by itself,
   but a maintainability/consistency risk worth flagging for Phase 2 — any UX fix made to "how
   partner panels animate" today would need to be copy-pasted 34+ times to land everywhere.
5. **Silent error-swallowing is the dominant error-handling pattern in the partner admin hooks**
   (`useAdminAnalyticsPanel.ts`, `useAdminAuditTrailPanel.ts`, `useAdminPartnersPanel.ts`,
   `useAdminSystemHealthPanel.ts`, `useAdminVerificationPanel.ts`, etc.): nearly every
   `getRequest`/`postRequest` call passes `{ errorMessage: '' }` and the `catch` block is often a
   bare `catch { }` with no `setError(...)` call at all — a failed admin-panel fetch just leaves
   stale or empty state with zero user-visible feedback, no retry affordance. Several legal/static
   screens (`PrivacyPolicyScreen.tsx`, `TermsAndConditionsScreen.tsx`,
   `GlobalSearchScreen.tsx`'s wrapper) have **no loading/error/empty states at all**, which is
   appropriate for static content but is flagged below per-file since the instructions call for
   listing what was actually found vs. not found, not what's "expected."
6. **Two screens with the same purpose live in parallel for Blocked Contacts** — the registered
   one is `src/screens/tabs/BlockedContactsScreen.tsx` (route `"BlockedContacts"`, imported in
   `App.tsx`); there is no conflicting duplicate in this scope, but note `blockContact()` (the
   exported helper, not just the component) is imported directly by
   `src/Module/ChatRoom/ChatRoomHandlers.tsx` — so this file is both a screen and a shared utility
   module, a mixed responsibility worth flagging for the audit phase.
